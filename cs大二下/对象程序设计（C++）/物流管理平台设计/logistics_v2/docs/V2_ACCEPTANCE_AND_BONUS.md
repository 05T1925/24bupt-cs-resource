# V2 验收与加分点设计

## 1. 必做验收点对应关系

| 实验要求 | V2 设计落点 |
| --- | --- |
| 快递员角色 | `Courier`、`CourierRepository`、快递员登录菜单 |
| 管理员添加和删除快递员 | 管理员菜单：新增、删除/停用、冻结/解冻 |
| 不同身份不同权限 | 主菜单分身份登录，业务层权限兜底 |
| 易碎品、图书、普通快递 | `FragileItem`、`BookItem`、`NormalItem` |
| 物品基类虚函数 `getPrice()` | `ExpressItem::getPrice()`，寄件扣费实际调用 |
| 待揽收、待签收、已签收 | `ExpressStatus` 三状态 |
| 管理员分配快递员 | `assignCourier()` |
| 快递员揽收 | `pickupExpress()`、批量揽收 |
| 揽收后 50% 费用转给快递员 | 业务层资金流转和日志 |
| 快递员任务查询 | `queryCourierExpresses()` |
| 管理员查看快递员和任务 | 快递员列表、任务统计、全局查询 |
| 错误处理 | 输入校验、余额不足、越权、重复操作、文件异常 |

## 2. 建议重点展示的亮点

### 2.1 多态计费不是摆设

演示方式：

1. 寄普通快递，输入重量 `3 kg`，费用为 `15.00`。
2. 寄图书，输入 `4 本`，费用为 `8.00`。
3. 寄易碎品，输入重量 `2 kg`，费用为 `16.00`。

讲解点：

- UI 只收集类型和数量。
- 业务层创建对应 `ExpressItem` 子类。
- 统一调用基类指针/引用上的 `getPrice()`。
- 这体现虚函数和多态。

### 2.2 权限控制在业务层

演示方式：

- 快递员 A 尝试揽收分配给快递员 B 的快递，系统拒绝并写日志。
- 用户尝试签收别人的快递，系统拒绝并写日志。

讲解点：

- 菜单隐藏不是安全边界。
- `LogisticsSystem` 会统一检查权限。

### 2.3 资金流闭环

演示方式：

- 用户寄件后余额减少，管理员余额增加。
- 快递员揽收后，管理员余额减少该单 50%，快递员余额增加。

讲解点：

- 资金变化和状态变化在同一业务操作中完成。
- 保存失败时应回滚内存状态，避免账实不一致。

### 2.4 审计日志

演示方式：

- 查看寄件、分配、揽收、签收、越权、失败操作日志。
- 如果实现哈希链，可演示日志完整性校验。

讲解点：

- 管理员可追踪系统关键操作。
- 日志只允许管理员查看。

## 3. 合理完善项

这些不是题目硬性要求，但适合作为加分点：

- 快递员冻结/解冻。
- 快递员离职逻辑删除，保留历史任务。
- 批量揽收、全部揽收。
- 查询条件对象化。
- 原子化文件保存。
- 日志哈希链。
- 登录失败次数持久化。
- 管理员统计看板：
  - 平台余额。
  - 快递员总收入。
  - 待揽收/待签收/已签收数量。
  - 各快递员任务数。
  - 各物品类型收入。

## 4. 需要避免的扣分风险

- 只定义了 `getPrice()`，但寄件时没有调用它。
- 快递员可以揽收任何人的任务。
- 用户寄件后仍直接进入待签收，漏掉待揽收状态。
- 管理员没有分配快递员流程。
- 揽收后没有给快递员转 50%。
- 快递员查询能看到其他快递员的任务。
- 新增 `couriers.txt` 明文保存密码。
- 删除快递员导致历史快递记录找不到负责人。
- 输入重量、册数、菜单、账号时缺少校验。
- 修改 V1 中文控制台方案导致乱码复发。

## 5. 推荐验收脚本

```text
1. 启动 V2，展示主菜单有用户、快递员、管理员三种身份。
2. 管理员登录，新增快递员 courier001。
3. 注册 user001、user002，并为 user001 充值。
4. user001 寄三种类型快递给 user002，展示多态计费。
5. 管理员查询待揽收快递，并分配给 courier001。
6. courier001 登录，查看待揽收任务，批量揽收。
7. 展示快递状态变为待签收，快递员收入增加，管理员余额扣除 50%。
8. user002 登录，查看未签收快递，批量签收。
9. user001/user002/courier001/admin 分别查询，展示权限边界。
10. 演示非法输入、余额不足、越权操作和日志记录。
```
