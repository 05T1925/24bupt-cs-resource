# V2 实验要求拆解

## 1. 题目定位

题目二是“快递员任务管理子系统”，是在题目一单机版基础上增加角色、任务流和多态计费。它仍是单机版，一个程序、一个进程，不涉及网络通信。

V2 程序需要独立提交，不能只提交 V3 网络版，也不能只在 V1 上口头说明扩展。

## 2. 必做功能清单

### 2.1 角色体系

- 普通用户：注册、登录、充值、寄件、签收、查询自己的快递。
- 快递员：登录、查看自己的待揽收任务、揽收一个或多个任务、查询自己的任务、查看收入。
- 管理员：登录、管理用户、管理快递员、查询全部快递、分配快递员、查看日志和统计。

### 2.2 快递员管理

管理员需要支持：

- 添加快递员。
- 删除快递员。
- 查看快递员列表。
- 冻结或解冻快递员，作为实验要求之外的合理完善。

删除规则建议：

- 若快递员名下存在待揽收或待签收任务，不允许直接删除。
- 若只存在历史已签收任务，可以逻辑删除或标记离职。
- 为了便于审计，推荐使用“冻结/离职标记”替代物理删除；但菜单仍可命名为删除快递员，并在实现中记录为离职。

### 2.3 快递分类与计费

实验明确要求继承体系：

```text
ExpressItem 物品基类
  FragileItem 易碎品
  BookItem 图书
  NormalItem 普通快递
```

计费规则：

- 易碎品：`8 元/kg`
- 图书：`2 元/本`
- 普通快递：`5 元/kg`

`ExpressItem::getPrice()` 必须是虚函数，并且用户寄件扣费时必须实际调用它。验收时可以展示代码位置和运行结果。

### 2.4 快递状态

V2 状态为三种：

```text
待揽收
待签收
已签收
```

状态转换：

- 用户寄件成功：待揽收。
- 快递员揽收成功：待签收。
- 收件人签收成功：已签收。

### 2.5 资金流

用户寄件时：

- 根据快递类型和数量/重量计算费用。
- 从发件用户余额扣除。
- 转入管理员/物流公司账户。

快递员揽收时：

- 从管理员账户转出该快递费的 50%。
- 转入负责快递员账户。
- 快递员收入应持久化。

建议保留平台收入统计：

```text
平台毛收入 = 所有寄件费用
快递员支出 = 所有揽收提成
平台净收入 = 管理员当前余额
```

### 2.6 查询要求

用户查询：

- 只能看自己发出或接收的快递。
- 可按发件人、收件人、时间、单号查询。

快递员查询：

- 只能看自己名下揽收和投递任务。
- 可按发件人、收件人、时间、单号、状态查询。

管理员查询：

- 可看全部用户、全部快递、全部快递员任务。
- 可按用户、时间、单号查询。

### 2.7 错误处理

至少覆盖：

- 余额不足。
- 非法输入。
- 登录密码错误。
- 账号冻结。
- 收件人不存在。
- 快递员不存在或被冻结。
- 未分配快递员时揽收。
- 快递员揽收他人任务。
- 用户签收待揽收快递。
- 用户签收他人快递。
- 重复签收或重复揽收。
- 文件读取异常和保存失败。
