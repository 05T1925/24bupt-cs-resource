# v1_LOG01：Logistics_v1 架构与需求设计日志

## 1. 上下文吸收与核心考察点确认

本日志继承 `v1_LOG00` 的设计结论，记录 `logistics_v1` 当前阶段的真实系统状态、近期修复、错误复盘和后续扩展方向。

当前项目定位为：基于 C++ 面向对象思想实现的《物流管理系统》单机控制台版。系统不只是简单菜单程序，而是围绕课程验收中的功能完整性、异常处理、安全机制、权限控制、日志审计、文件持久化、终端交互和后续可扩展性进行设计。

当前核心考察点保持不变：

- **终端交互：** 采用清晰页面式 CLI，菜单层级明确，表格输出统一，用户操作有确认和错误提示。
- **面向对象架构：** 业务逻辑不能堆在 `main()`，必须体现实体类、仓储类、业务服务类、UI 流程类和工具类的职责分离。
- **const 约束：** 不修改对象状态的函数尽量标注 `const`，便于解释代码规范性。
- **快捷操作：** 寄件必须提供物品描述快捷选项，收件必须支持单个签收、批量签收、全部签收。
- **完整输入检查：** 用户名、姓名、电话、地址、密码、金额、菜单、快递单号、时间、日志筛选、批量签收序号等都必须校验。
- **密码安全：** 密码必须由字母和数字组成，禁止明文存储，采用 salt + SHA-256 哈希。
- **权限控制：** 普通用户只能查询与自己相关的快递，管理员才能查看全局数据和日志。
- **异常工况：** 覆盖余额不足、文件保存失败、数据文件异常行、快递单号冲突、重复签收、越权签收等场景。
- **日志追踪：** 注册、登录、寄件、签收、查询、冻结、保存失败、数据异常等关键操作必须写入日志，且日志仅管理员可见。
- **高级搜索：** 快递查询支持发件人、收件人、单号、时间范围、状态等多条件复合筛选。

## 3. 本阶段重要修改记录

### 3.1 中文终端显示方案修复

近期曾出现严重终端显示问题，表现包括：

- 中文菜单完全不显示，只剩分隔线。
- 中文变成乱码或 `�`。
- 直接双击 `src/main.exe` 和通过 `run.bat` 运行时表现不一致。
- 曾错误尝试单纯使用 `chcp 65001`、单纯 GBK 编译、单纯切换控制台代码页等方案，但这些方案在用户本机终端中并不稳定。

最终采用的方案：

- 源码文件继续按 UTF-8 保存。
- `build.bat` 使用 `-finput-charset=UTF-8 -fexec-charset=GBK`，将字符串常量编译为中文 Windows 控制台更稳定的 GBK 字节。
- `run.bat` 使用 `chcp 936`。
- Windows 下增加 `WindowsConsoleOutputBuffer`，将输出的系统中文代码页文本转换为 UTF-16，再通过 `WriteConsoleW` 写入控制台。
- 程序初始化时使用系统 ANSI 代码页设置输入输出，避免中文输入和输出编码不一致。

后续红线：

- 不要轻易改动当前中文显示方案。
- 不要重新混用 UTF-8 输出和 GBK 输出。
- 修改显示相关代码后必须重新运行 `build.bat`，确认 `bin/logistics_v1.exe` 和 `src/main.exe` 同时刷新。
- 用户截图中标题栏出现“选择”时，说明控制台进入选择模式，应按 `Esc` 退出，否则程序会暂停。

### 3.2 README 编码说明同步

此前 README 仍写着：

```text
UTF-8 控制台输出
chcp 65001
```

这与当前真实实现不符，已更新为：

- 源码 UTF-8 保存。
- 编译时字符串常量转 GBK。
- 运行脚本切换到 936。
- 输出时转 UTF-16 写入 Windows 控制台。

这点非常重要，因为 README 必须和代码一致，否则验收时老师按文档检查会发现矛盾。

### 3.3 金额输入校验修复

此前 `tryParsePositiveMoney()` 只判断正数和无多余字符，没有真正限制“两位小数”。因此输入：

```text
1.234
```

会被接受，并在显示或保存时变成：

```text
1.23
```

这属于静默金额变化，和 README 中“最多保留两位小数”的承诺不一致。

当前已修复：

- 金额必须为正数。
- 最多两位小数。
- 拒绝空字符串、负数、字母、科学计数法、多个小数点、`.5`、`1.`、`1.234` 等格式。
- 金额解析使用完整解析，不接受 `12abc` 这种半截合法文本。

### 3.4 业务层注册校验补强

此前菜单层注册时会调用姓名和地址完整校验，但业务层 `registerUser()` 只使用 `isNotBlank()`，没有使用：

```cpp
InputValidator::isValidName()
InputValidator::isValidAddress()
```

这意味着如果未来绕过 UI 层调用业务层，可能把超长姓名或非法地址写入系统。

当前已修复：

- `LogisticsSystem::registerUser()` 也使用完整姓名校验。
- `LogisticsSystem::registerUser()` 也使用完整地址校验。
- UI 层和业务层形成双层防护。

### 3.5 saveAll 返回值检查与失败回滚

此前多个业务流程调用 `saveAll()` 后没有检查返回值，例如：

- 注册。
- 修改密码。
- 充值。
- 寄件。
- 签收。
- 冻结/解冻。

风险是：文件被占用、权限不足或磁盘异常时，程序可能提示“成功”，但数据并没有落盘。

当前已修复：

- 增加统一保存失败处理函数 `reportSaveFailure()`。
- 注册保存失败时移除刚加入的用户。
- 改密保存失败时恢复旧 salt 和旧 hash。
- 充值保存失败时恢复旧余额。
- 寄件保存失败时移除新增快递、退回运费、回滚管理员账户收入。
- 签收保存失败时恢复旧快递状态。
- 冻结/解冻保存失败时恢复旧冻结状态。
- 保存失败会写入日志，并提示“操作已回滚”。

### 3.6 数据文件反序列化校验补强

此前数据文件读取中，余额和费用使用流读取，可能接受：

```text
12abc
```

并解析为 `12`。这不够严格。

当前已修复：

- 用户余额必须完整解析为合法非负数。
- 管理员余额必须完整解析为合法非负数。
- 快递费用必须完整解析为合法正数。
- 用户冻结字段必须严格为 `0` 或 `1`。
- 非法数据行会被跳过并计入启动日志。

### 5.4 完整输入检查

当前已覆盖：

- 用户名：3-20 位，只允许字母、数字、下划线。
- 姓名：不能为空，不能包含控制字符，长度不超过 30 个字符。
- 电话：必须为 11 位数字。
- 地址：不能为空，长度 2-80 个字符，不能包含控制字符。
- 密码：6-30 位，必须同时包含字母和数字，不能包含空白字符。
- 金额：正数，最多两位小数。
- 菜单项：必须在合法范围内。
- 物品描述：不能为空，长度不超过 60 个字符。
- 快递单号：可空；非空时必须以 `EX` 开头，只能包含字母和数字。
- 查询时间：可空；非空时必须符合 `YYYY-MM-DD HH:MM:SS`，并检查真实日期。
- 状态筛选：只能选择全部、待签收、已签收。
- 日志结果筛选：只能是 `SUCCESS`、`FAILED`、`DENIED` 或空。
- 日志关键字：限制长度，禁止控制字符。

### 5.5 密码安全机制

密码策略：

- 密码必须同时包含字母和数字。
- 密码不能包含空白字符。
- 注册和改密都要求二次确认。
- 改密必须输入旧密码。
- 新密码不能与旧密码相同。
- 密码不明文保存。
- 保存格式为 salt + SHA-256 hash。

登录策略：

- 用户登录最多尝试 3 次。
- 管理员登录最多尝试 3 次。
- 密码错误写入日志。
- 冻结用户不能登录。

### 5.6 权限控制

## 6. 本阶段新增创新优化点

以下创新点用于后续迭代，不一定全部立刻落地，但设计上已和当前架构兼容。

### 6.1 原子化文件保存与备份恢复

当前已检查 `saveAll()` 返回值并做业务回滚，但文件保存仍是直接覆盖写入。

后续可升级为：

```text
写 users.txt.tmp
写入成功后备份 users.txt 为 users.txt.bak
再 rename tmp 为正式文件
失败时恢复 bak
```

价值：

- 防止断电或程序中断导致半文件。
- 文件被占用时能保留旧数据。
- 更接近真实工程中的可靠持久化。
- 可以作为“文件异常工况覆盖”的高级加分项。

### 6.2 查询条件对象化

当前查询函数参数较长：

```text
sender, receiver, id, startTime, endTime, statusFilter
```

可新增：

```cpp
class ExpressQueryCondition {
public:
    std::string sender;
    std::string receiver;
    std::string expressId;
    std::string startTime;
    std::string endTime;
    int statusFilter;
};
```

价值：

- 降低函数参数复杂度。
- 用户查询和管理员查询复用同一条件对象。
- 未来增加快递员、物品类别、费用区间时不需要继续拉长参数表。
- 体现更工程化的数据建模能力。

### 6.3 业务异常类体系

当前主要通过 `bool + message` 传递错误。

后续可增加异常类：

```cpp
class LogisticsException;
class InputException;
class AuthException;
class PermissionException;
class BalanceException;
class StorageException;
```

价值：

- 错误类型更清晰。
- UI 层可以统一捕获并展示。
- 日志可以记录异常类型。
- 更符合大型 C++ 项目的异常处理风格。

### 6.4 审计日志哈希链

当前日志可以记录事件，但普通文本日志仍可能被外部篡改。

后续可升级为：

```text
序号 | 时间 | 操作人 | 操作 | 结果 | 详情 | prevHash | currentHash
```

价值：

- 任意中间日志被修改后，后续哈希链会断裂。
- 管理员可以进行日志完整性检查。
- 与“安全保障”和“系统级日志追踪”高度契合。

### 6.5 多态计费与角色扩展

后续 `logistics_v2` 可以引入：

```cpp
class Person;
class User : public Person;
class Admin : public Person;
class Courier : public Person;

class ExpressItem;
class DocumentItem : public ExpressItem;
class FragileItem : public ExpressItem;
class FoodItem : public ExpressItem;
```

价值：

- 自然体现继承和多态。
- 不同物品类型通过虚函数计算费用。
- 快递员角色可以扩展揽收、派送和收入统计。
- 比单纯菜单功能更贴近 C++ 面向对象课程要求。

## 7. 当前仍可优化的问题

### 7.1 文件保存尚未完全原子化

虽然当前已检查保存失败并回滚内存状态，但仓储层仍然直接写正式文件。极端情况下，如果写到一半断电，仍可能出现文件损坏。

后续建议优先实现原子保存。

### 7.2 表格中文对齐仍依赖控制台字体

当前中文已经能显示，但表格使用 `std::setw`，它对中文宽度并不完全可靠。不同终端字体下，中文列可能轻微错位。

后续可实现中英文混合宽度计算，或缩短中文字段列宽展示。

### 7.3 数据目录识别仍依赖相对路径

当前程序会根据当前目录是否存在 `src/bin` 或 `../src/../bin` 判断主数据目录。一般从根目录、`bin`、`src` 启动没有问题，但如果从项目内更深层目录运行，仍可能误判。

后续可改为根据可执行文件路径定位项目根目录。

### 7.4 登录失败“锁定”目前是单次流程限制

当前实现是用户或管理员登录连续 3 次失败后返回上级菜单。严格意义上不是永久锁定账号。

如果老师强调“输错 3 次锁定”，后续可升级为：

- 用户对象增加登录失败次数。
- 连续失败 3 次自动冻结。
- 管理员可解冻。
- 日志记录锁定原因。

## 8. 验收展示建议

建议按以下顺序演示：

1. 启动程序，展示中文菜单正常显示。
2. 注册用户，演示用户名、手机号、密码、金额等非法输入会被拦截。
3. 注册两个用户，例如 `user001` 和 `user002`。
4. 登录 `user001`，展示顶部状态栏：姓名、余额、未签收数量。
5. 充值，演示 `1.234` 被拒绝，`20.00` 被接受。
6. 选择物品描述快捷选项，向 `user002` 寄件，展示扣费和快递单号。
7. 登录 `user002`，展示未签收快递，演示单个/批量/全部签收。
8. 用户查询快递，演示多条件搜索。
9. 尝试普通用户查询他人单号，说明越权不返回数据并写日志。
10. 管理员登录，查看用户、快递、日志。
11. 管理员按 `DENIED` 或 `FAILED` 筛选日志。
12. 管理员冻结用户，演示被冻结用户不能登录。

## 9. 后续修改红线

后续继续开发必须遵守：

- 不要随意改动当前中文控制台编码方案。
- 不要只改 `bin/logistics_v1.exe` 或只改 `src/main.exe`，必须通过 `build.bat` 同时刷新两个产物。
- 不要让 README 与真实代码实现不一致。
- 不要让密码明文进入数据文件。
- 不要绕过 `InputValidator` 接收用户输入。
- 不要只在 UI 层做校验，关键规则必须在业务层兜底。
- 不要忽略 `saveAll()` 返回值。
- 不要让普通用户绕过权限过滤。
- 不要删除关键操作日志。
- 不要让 `data`、`src/data`、`bin/data` 的主从关系变得无法解释。
- 每次修改后至少执行 `cmd /c build.bat`，并做一次主菜单或关键流程验证。

## 10. 当前版本总结

`logistics_v1` 当前已经从“基础菜单系统”推进到“具备安全意识、异常处理、日志审计、输入校验和持久化可靠性考虑的单机业务系统”。

当前最适合在验收中强调的亮点：

- 密码 salt + SHA-256。
- 普通用户权限过滤和越权日志。
- 完整输入校验。
- 快捷寄件和快捷签收。
- 管理员日志审计。
- 数据异常行跳过。
- 保存失败回滚。
- Windows 中文控制台兼容处理。
- 为 `logistics_v2` 的快递员、多态计费、原子化保存和日志哈希链预留设计空间。
