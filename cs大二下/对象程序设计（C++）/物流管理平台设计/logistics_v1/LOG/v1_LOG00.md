# v1_LOG00：Logistics_v1 架构与需求设计日志

## 1. 上下文吸收与核心目标确认

本项目是基于 C++ 面向对象思想实现的《物流管理系统》单机版，当前版本为 `logistics_v1`。项目目标不是简单完成菜单式功能，而是面向课程验收中的“功能完整性、异常处理、安全意识、交互体验、架构成熟度、日志审计”等考察点，构建一个结构清晰、输入稳定、安全可解释、便于后续扩展到 `logistics_v2` 的控制台业务系统。

当前项目目录：

```text
C:\Users\28641\Desktop\课设C++\物流管理平台设计\logistics_v1
```

当前默认管理员账号：

```text
账号：admin
密码：Admin0219
```

管理员密码不应明文出现在 `admin.txt` 中。数据文件保存的是管理员账号、姓名、随机盐、密码哈希和余额等字段。验收解释时应说明：登录时根据 salt 和用户输入密码重新计算哈希，再与文件中的哈希值比较。

必须坚持的核心考察点如下：

- 终端交互必须清晰，菜单层级合理，页面标题、提示、表格输出要统一。
- 架构必须完整，不能把业务逻辑堆在 `main()` 中。
- 类设计要符合高内聚、低耦合，能够说明每类职责。
- 不改变对象状态的成员函数应尽量标注 `const`。
- 寄件时必须提供“样品描述快捷选项”。
- 收件时必须提供“单个签收、批量签收、全部签收”等快捷操作。
- 所有输入都必须做合法性检查，不能只检查密码。
- 密码必须由字母和数字组成，禁止明文存储，使用 SHA-256 或同级哈希机制。
- 登录失败、余额不足、文件异常、越权查询、快递单号冲突等场景都要有处理。
- 普通用户不能越权查看与自己无关的快递。
- 系统必须记录关键操作日志，日志仅管理员可见。
- 快递查询必须支持多条件复合搜索。

## 3. 近期重要错误复盘

### 3.1 终端中文显示问题

近期修改过程中，终端中文显示曾多次出现问题，具体表现包括：

- 中文菜单显示成乱码。
- 中文内容被吞掉，只剩 `====` 分隔线等 ASCII 字符。
- `src/main.exe` 与 `bin/logistics_v1.exe` 编译产物大小一度不一致，说明实际运行文件可能不是最新构建产物。
- 曾尝试过多套编码方案，包括 UTF-8 控制台、GBK/936 控制台、自定义 `cout` 缓冲、`WriteConsoleW`、`CONOUT$` 等，但多次切换导致状态混乱。

后续必须遵守以下约束：

- 不要轻易改动控制台编码层。
- 不要同时混用多套输出方案。
- 修改显示相关代码后，必须同时重新编译 `bin/logistics_v1.exe` 和 `src/main.exe`。
- 编译前确认旧的 `main.exe` 或 `logistics_v1.exe` 窗口已经关闭，避免 Windows 锁定文件导致覆盖失败。
- 编译后检查两个 exe 的修改时间和文件大小是否一致或合理。
- 验证时至少运行一次主菜单，确认中文菜单完整显示。
- 如果后续再次处理中文显示，优先选择一种方案并全项目保持一致，避免局部 UTF-8、局部 GBK。

### 3.2 数据目录混乱问题

运行位置不同可能导致程序在 `data/`、`src/data/`、`bin/data/` 中生成不同数据文件。此前用户曾在 `src/data/admin.txt` 中看到旧管理员数据，因此后续必须注意：

- 业务真实数据目录应统一。
- 运行前要明确程序使用哪个 `data`。
- 若保留镜像目录，必须说明主数据目录和镜像目录的区别。
- 不要让 `admin.txt` 出现明文密码。
- 默认管理员应统一为 `admin / Admin0219`。

### 3.3 输入校验不完整问题

此前注册、查询等流程中，用户名、姓名、电话、地址、密码、查询条件等输入提示不够完整。后续必须保证：

- 所有用户输入都有校验。
- 校验失败必须给出明确原因。
- 不能让非法输入进入业务层。
- 菜单数字、金额、日期、批量签收序号等都要防止越界和非数字输入。

## 4. 核心架构设计思路

系统采用“实体类 + 仓储类 + 业务服务类 + UI 流程类 + 工具类”的分层结构。

### 4.1 实体类

`User`：普通用户实体，保存用户名、姓名、电话、密码盐值、密码哈希、余额、地址、冻结状态等。

`Admin`：管理员实体，保存管理员账号、姓名、密码盐值、密码哈希、公司账户余额等。

`Express`：快递实体，保存快递单号、发件人、收件人、寄送时间、签收时间、状态、物品描述、费用等。

`LogEntry`：日志实体，保存操作时间、操作人身份、操作人账号、操作类型、操作结果、详情。

### 4.2 仓储类

`UserRepository`、`AdminRepository`、`ExpressRepository` 负责文件持久化。

设计原则：

- 文件读写集中在仓储层。
- 业务层不直接散落文件操作。
- 数据字段采用统一分隔格式。
- 对特殊字符进行转义，防止文本字段破坏数据格式。
- 读取异常行时不让程序崩溃，应跳过异常行并记录日志。

### 4.3 业务服务类

`LogisticsSystem` 是核心业务层，负责：

- 注册、登录、改密。
- 充值、扣费。
- 寄件、签收。
- 查询、权限过滤。
- 冻结、解冻。
- 日志记录。
- 数据保存。

关键原则：

- 权限判断必须放在业务层，而不是只依赖菜单隐藏。
- 普通用户查询必须先过滤“与自己相关”的快递，再做条件筛选。
- 关键操作必须落日志。
- 业务失败也应记录，例如登录失败、余额不足、越权查询。

### 4.4 UI 与流程类

`ConsoleUI` 负责：

- 页面标题。
- 菜单输出。
- 表格输出。
- 字符串、整数、金额读取。
- 确认操作。
- 暂停等待。

`App` 负责：

- 主菜单流程。
- 用户注册流程。
- 用户登录流程。
- 用户功能菜单。
- 管理员登录流程。
- 管理员功能菜单。

设计说明：

- UI 层只负责交互和参数收集。
- UI 层拿到输入后先调用 `InputValidator` 校验。
- 合法数据再传给 `LogisticsSystem`。
- 这样验收时可以说明“非法输入不会进入核心业务层”。

### 4.5 工具类

`StringUtil`：字符串裁剪、时间格式、金额格式、数字判断等。

`InputValidator`：集中管理用户名、姓名、电话、地址、密码、金额、时间、快递单号等输入规则。

`SHA256`：计算 SHA-256 摘要。

`PasswordHasher`：负责生成 salt、计算密码哈希、验证密码。

`DirectoryUtil`：负责目录创建、路径拼接、数据目录识别。

`Logger`：负责写入和读取操作日志。

## 5. 加分项实现方案

### 5.1 终端交互

系统应采用页面式 CLI，而不是零散输出。

典型页面包括：

- 主菜单。
- 用户注册页。
- 用户登录页。
- 用户功能菜单。
- 管理员登录页。
- 管理员功能菜单。
- 查询结果页。
- 日志查看页。

交互细节：

- 页面标题统一。
- 分隔线统一。
- 菜单编号清晰。
- 输入错误后提示重新输入。
- 查询结果表格展示。
- 扣费、充值、签收等关键操作前确认。
- 用户菜单顶部显示当前用户、余额、未签收数量。

### 5.2 样品描述快捷选项

寄件时提供快捷描述：

```text
1. 文件资料
2. 衣物鞋帽
3. 数码配件
4. 食品零食
5. 日用品
6. 自定义输入
```

该设计可以提升交互体验，减少空描述和非法描述。

### 5.3 接收快递快捷选项

收件人查看未签收快递后提供：

```text
1. 签收单个
2. 批量签收
3. 全部签收
0. 返回
```

批量签收支持输入多个序号，例如：

```text
1 2 3
1,2,3
```

系统需要跳过非法序号、重复序号和越界序号，并给出提示。

### 5.4 完整输入检查

必须覆盖以下输入：

- 用户名：3-20 位，只允许字母、数字、下划线。
- 姓名：不能为空，长度合理，不能包含控制字符。
- 电话：必须为 11 位数字。
- 地址：不能为空，长度合理，不能包含控制字符。
- 密码：6-30 位，必须同时包含字母和数字，不能包含空白字符。
- 金额：必须为正数，最多保留两位小数。
- 菜单：必须在合法范围内。
- 物品描述：不能为空，长度合理。
- 收件用户：必须存在，不能被冻结，不能是自己。
- 快递单号：格式必须合法，不存在时要提示。
- 时间筛选：必须符合 `YYYY-MM-DD HH:MM:SS`。
- 状态筛选：只能选择全部、待签收、已签收。
- 批量签收序号：必须是数字，且不能越界。
- 日志筛选：操作人、操作类型、结果均需校验。

### 5.5 密码安全机制

密码保存采用：

```text
salt + SHA-256
```

验证流程：

```text
用户输入密码
读取该用户 salt
重新计算 hash
与文件中的 passwordHash 比较
成功则登录
失败则提示并记录日志
```

要求：

- 不保存明文密码。
- 注册和改密都检查密码复杂度。
- 改密前必须输入旧密码。
- 新旧密码不能相同。
- 登录失败最多尝试 3 次。

### 5.6 权限控制

普通用户只能查看：

- 自己发出的快递。
- 自己接收的快递。

普通用户不能通过输入他人用户名或快递单号查看无关快递。

管理员可以查看所有用户、所有快递和系统日志。

权限控制必须位于 `LogisticsSystem`，不能只依赖 UI 层。

### 5.7 日志系统

日志文件：

```text
data/operations.log
```

日志字段：

```text
时间 | 操作人身份 | 操作人账号 | 操作类型 | 操作结果 | 详情
```

记录场景：

- 系统启动。
- 用户注册。
- 用户登录成功和失败。
- 管理员登录成功和失败。
- 修改密码。
- 充值。
- 发送快递。
- 签收快递。
- 查询快递。
- 越权查询。
- 管理员查看日志。
- 管理员冻结/解冻用户。
- 数据读取异常。
- 数据保存失败。

日志仅管理员可见。

### 5.8 高级搜索

快递查询支持：

- 发件人。
- 收件人。
- 快递单号。
- 开始时间。
- 结束时间。
- 快递状态。

普通用户查询流程：

```text
先过滤出与当前用户相关的快递
再根据查询条件筛选
最后展示结果
```

管理员查询流程：

```text
在全部快递中根据条件筛选
```

## 6. 新增创新优化点

### 6.1 查询条件对象化

新增 `ExpressQueryCondition` 类，将查询条件从多个零散参数封装为一个对象。

示例字段：

```text
sender
receiver
expressId
startTime
endTime
status
```

价值：

- 避免查询函数参数过长。
- 普通用户查询和管理员查询可以复用同一套条件对象。
- 后续 `logistics_v2` 增加快递员角色时可以继续复用。
- 便于将来扩展到文件导出或网络请求。

### 6.2 业务异常类体系

设计异常类层次：

```cpp
class LogisticsException;
class InputException;
class AuthException;
class PermissionException;
class BalanceException;
class StorageException;
```

价值：

- 错误类型清晰。
- UI 层可以统一捕获并显示友好提示。
- 日志系统可以记录异常类型。
- 比单纯返回字符串更工程化。

### 6.3 原子化保存与备份恢复

数据保存从直接写文件升级为：

```text
写入 users.txt.tmp
成功后备份旧 users.txt 为 users.txt.bak
再替换正式 users.txt
```

价值：

- 避免程序中断导致数据文件损坏。
- 文件被占用时能给出明确错误。
- 出现异常时可以尝试从 `.bak` 恢复。
- 体现对持久化可靠性的考虑。

### 6.4 审计日志哈希链

日志可升级为防篡改结构：

```text
日志编号 | 时间 | 操作人 | 操作 | 结果 | 详情 | 上一条Hash | 当前Hash
```

价值：

- 管理员可以检测日志是否被人为修改。
- 与安全审计加分项高度契合。
- 能体现系统不是只有业务功能，还有追踪与审计意识。

### 6.5 C++ 多态预留点

为 `logistics_v2` 预留多态扩展：

```cpp
class Person;
class User : public Person;
class Admin : public Person;
class Courier : public Person;

class ExpressItem;
class DocumentItem : public ExpressItem;
class FragileItem : public ExpressItem;
class FoodItem : public ExpressItem;
```

价值：

- `v1` 保持简单稳定。
- `v2` 可以自然引入继承、多态、虚函数。
- 快递费用可由不同物品类型多态计算。
- 更贴合 C++ 面向对象课程考察。

## 9. 后续修改红线

后续继续开发时必须遵守：

- 不要随意更改控制台编码方案。
- 不要让源码中重新出现旧管理员密码 `Admin123`。
- 不要把密码明文写入数据文件。
- 不要绕过 `InputValidator` 直接接受用户输入。
- 不要把业务逻辑重新堆回 `main()`。
- 不要让普通用户查询绕过权限过滤。
- 不要删除日志记录。
- 不要让 `src/data`、`bin/data`、根目录 `data` 之间出现无法解释的冲突。
- 每次改完必须重新编译并至少验证主菜单、管理员登录、一次异常输入提示。
