## 3. 协议层详细验证

### 3.1 帧格式

- 请求帧：`REQ|command|token|argCount|arg1|arg2|...\n`
- 响应帧：`RES|1/0|code|message|recordCount|record1|record2|...\n`

### 3.2 转义规则

```
%  → %25
|  → %7C
\n → %0A
\r → %0D
```

所有字段由 `ProtocolCodec` 统一 escape/unescape，上层业务无需手动处理。未知或不完整转义序列抛出 `ProtocolError`。

### 3.3 安全限制

```
MaxMessageLength = 8192
MaxFieldLength   = 1024
MaxVectorItems   = 256
```

### 3.4 TCP 流式处理

- **服务端**：`SocketServer::handleClient` 维护 `std::string buffer`，recv 后 append，按 `\n` 循环提取完整帧。buffer 超过 `MaxMessageLength * 2` 时返回 `PROTOCOL_ERROR` 并断开连接。
- **客户端**：`SocketClient::receiveFrame` 维护 `receiveBuffer_`，同样按 `\n` 截帧。超过限制抛出 `ProtocolError`。
- **sendAll**：服务端和客户端均有 sendAll 循环处理 partial send。
- **命令校验**：只允许大写字母、数字和下划线，空命令拒绝，未知命令返回 `UNKNOWN_COMMAND`。
- **参数校验**：`argCount`/`recordCount` 与实际字段数不一致时返回 `PROTOCOL_ERROR`。
- **异常兜底**：`ProtocolError`、`std::exception` 均被 catch 并转换为结构化 `ERR|code|message` 响应，不会抛出到进程外。

## 4. Session 与权限详细验证

### 4.1 Token 生成

```
SHA-256(username | role | high_resolution_clock ticks | random_device随机数A | random_device随机数B | this指针)
```

64 位十六进制字符串。

### 4.2 Session 结构

```cpp
struct Session {
    std::string token;
    std::string username;
    std::string role;
    std::string loginTime;
    std::string lastActiveTime;
};
```

### 4.3 权限分流矩阵

| 身份 | 可执行命令 |
|------|-----------|
| GUEST（无 token） | `REGISTER_USER`、`LOGIN_USER`、`LOGIN_COURIER`、`LOGIN_ADMIN`、`PING` |
| USER | `QUERY_BALANCE`、`RECHARGE`、`SEND_EXPRESS`、`QUERY_MY_EXPRESS`、`QUERY_WAITING_SIGN`、`SIGN_EXPRESS`、`SIGN_BATCH`、`CHANGE_PASSWORD` |
| COURIER | `QUERY_MY_PICKUP_TASKS`、`PICKUP_EXPRESS`、`PICKUP_BATCH`、`QUERY_MY_TASKS`、`VIEW_MY_PERFORMANCE` |
| ADMIN | `QUERY_USERS`、`SET_USER_FROZEN`、`CREATE_COURIER`、`REMOVE_COURIER`、`SET_COURIER_FROZEN`、`QUERY_COURIERS`、`ASSIGN_COURIER`、`AUTO_ASSIGN_COURIER`、`AUTO_ASSIGN_ALL`、`QUERY_ALL_EXPRESS`、`QUERY_LOGS`、`VERIFY_LOG_CHAIN`、`VIEW_DASHBOARD`、`VIEW_COURIER_PERFORMANCE` |

### 4.4 越权审计

- `requireAdminSession`：非 ADMIN → 返回 `PERMISSION_DENIED` + 写 `ADMIN_PERMISSION_DENIED` 审计日志
- `requireCourierSession`：非 COURIER → 返回 `PERMISSION_DENIED` + 写 `COURIER_PERMISSION_DENIED` 审计日志
- `requireUserSession`：非 USER → 返回 `PERMISSION_DENIED`
- 审计日志写入 `operations.log`，不包含明文密码或完整 token

### 4.5 登录安全

- 密码 SHA-256 加盐哈希存储
- USER/COURIER 连续 3 次失败 → 自动冻结（frozen=1）
- ADMIN 不自动冻结（避免系统锁死）
- 登录成功后 failedCount 清零

## 7. 风险与问题识别

### 7.1 中危：saveAll() 非原子事务

`LogisticsSystem::saveAll()` 依次调用 5 个 repository 的 `save()`：

```cpp
bool LogisticsSystem::saveAll() {
    return userRepository_.save(users_) &&
           adminRepository_.save(admin_) &&
           courierRepository_.save(couriers_) &&
           expressRepository_.save(expresses_) &&
           authStateRepository_.save(authStates_);
}
```

每个 `save()` 使用 `saveLinesAtomically`（.tmp → .bak → 正式文件），但 5 个 save 之间没有事务协调。

**场景**：`pickupExpress` 中，如果前 4 个 save 成功，第 5 个失败，内存中已回滚对象，但磁盘上前 4 个文件已被新数据覆盖。最坏情况下 server 重启可能读到不一致状态（如管理员已扣款但快递员未增加收入）。

**当前缓解**：5 个文件保存顺序固定，且每个 `saveLinesAtomically` 有 .bak 备份。实际触发概率极低（需要磁盘满或权限变更），且回滚恢复的是内存对象而磁盘文件是逐个覆盖的。`&&` 短路意味着第一个失败的 save 会阻止后续 save，所以不会出现"部分文件已更新、部分未更新"的情况，但"已更新的文件不会被回滚到旧状态"是真实问题。

**建议**：如需加固，可改为先写全部 .tmp，全部成功后再统一 rename（简化版 two-phase commit），或至少在对资金流关键的 `pickupExpress` 中做额外保护。

### 7.2 低危：快递单号 ID 基于 expresses_.size()

```cpp
stream << "EX" << std::setw(6) << std::setfill('0') << (expresses_.size() + 1U);
```

如果将来支持删除快递或清空重建 expresses_，会出现 ID 重用。当前因为只追加不删除，不会出问题。

### 7.3 低危：自测数据持续追加

每次运行 `--selftest-*` 都向 `data/server/` 追加新账号、快递和日志。长期运行后数据文件膨胀。演示前建议备份或重置数据目录。

### 7.4 低危：AUTO_ASSIGN_ALL 批量分配行为

`autoAssignAllWaitingPickup` 在同一个锁内逐单调用 `selectBestCourierIndex()`，后者每次都从 couriers 内存态重新计算负载。由于前一单分配已写入内存（`express.assignCourier`），后续 `selectBestCourierIndex()` 会反映已增的负载。**这是正确的增量行为**，但 LOG_SUM01 中提到"与 V2 快照算法有差异"。当前实现逻辑合理，不是 bug。

### 7.5 信息：MinGW std::mutex 编译问题

LOG_SUM01 和 LOG09 均记录：当前 MinGW 环境 `std::mutex`/`std::shared_mutex`/`std::filesystem` 编译不稳定。工程因此使用 `CoreMutex`/`CoreLock` 和 `SessionMutex`/`SessionLock`（基于 `std::atomic_flag` 自旋锁）。**不要轻易替换为标准库锁，除非确认工具链已升级且编译通过。**

## 10. 后续优化开发建议

### 10.1 优化原则

- 小步修改，避免大重构
- 优先修 correctness、安全、并发一致性、验收风险
- 不破坏现有构建脚本
- 不引入第三方依赖
- 不把 common 重新污染为 UI 层
- 不让 client 直接读写 data
- 不让业务身份依赖客户端传来的 username
- 不把明文密码或完整 token 写入日志
