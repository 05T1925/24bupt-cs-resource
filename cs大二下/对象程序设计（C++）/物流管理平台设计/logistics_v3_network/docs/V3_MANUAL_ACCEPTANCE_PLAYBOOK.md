# Logistics V3 人工验收展示手册

> 适用方式：服务端独立运行，后续主要使用交互式客户端人工展示  
> 建议时长：基础业务 6-8 分钟，创新亮点 3-5 分钟，提问 3-5 分钟

## 1. 演示前准备

建议准备 4 个终端窗口：

| 窗口 | 用途 |
|---|---|
| Server | 服务端持续监听，展示连接、请求摘要和断线日志 |
| Client-A | 发件用户、收件用户操作 |
| Client-B | 管理员操作 |
| Client-C | 快递员操作或并发自测 |

### 1.1 可选：验收前重新构建

```powershell

.\build_all.bat
```

预期生成：


可说明：

> server 和 client 是两个独立编译产物。客户端没有链接 LogisticsSystem 和 Repository，无法绕过服务端直接操作业务数据。

### 1.2 启动服务端

Server 窗口：

## 3. 人工业务闭环

## 3.1 注册两个普通用户

Client-A 启动后：

```text
1. 注册普通用户
```

先注册 `accsendNN`，再返回主菜单注册 `accrecvNN`。

展示点：

- 客户端先进行基本格式检查。
- 客户端通过 `CHECK_USERNAME_AVAILABLE` 请求服务端查重。
- 服务端再次执行完整校验，客户端校验不能替代服务端校验。
- 密码输入以 `*` 显示。

讲解：

> 校验有两层。客户端校验用于改善体验，服务端校验才是真正安全边界，因为客户端程序和网络数据都不能被信任。

## 4. 必须展示的基础要求

建议明确展示以下项目，避免只展示加分功能却漏掉题目基本要求：

1. server/client 是两个独立进程和两个独立 exe。
2. 服务端监听 9000 端口，客户端通过 Socket 请求。
3. 客户端不直接读写 `data/server`。
4. 普通用户注册、登录、充值、寄件、查询、签收。
5. 管理员管理快递员并分配订单。
6. 快递员查看任务并揽收。
7. 数据持久化：重启服务端后数据仍存在。
8. 不同角色权限隔离。
9. 输入错误或状态错误会返回明确错误码。

## 5. 优先展示的创新亮点

时间不足时按以下顺序展示。

### 亮点一：自定义协议与 TCP 流式分帧

展示源码：

```text
common/protocol/ProtocolCodec.h
server/SocketServer.cpp
client/SocketClient.cpp
```

得分点：

- `REQ/RES` 自定义文本协议。
- `\n` 标记消息边界。
- `%25/%7C/%0A/%0D` 字段转义。
- 单帧、单字段、参数数量上限。
- 客户端与服务端都处理半包、粘包和 partial send。

一句话：

> TCP 只保证有序字节，不提供消息边界，所以我在应用层设计了换行分帧和接收缓冲区。

### 亮点二：Token 零信任与三角色权限

展示源码：

```text
server/SessionManager.cpp
server/ServerController.cpp
```

得分点：

- 登录成功后服务端创建 Token。
- 每个业务请求重新根据 Token 解析角色和账号。
- 用户、快递员、管理员路由隔离。
- 越权请求返回 `PERMISSION_DENIED` 并记录审计。
- 重复登录拦截，断线清理 Session。

一句话：

> 客户端菜单不能代表权限，真正身份只由服务端 Session 中的 Token 映射决定。

### 亮点三：并发抢单保护

指令：

先退出或关闭所有交互式客户端，确保管理员等演示账号不再占用 Session。保持 Server 窗口运行，然后执行：


预期：

得分点：

> 网络层可以并发，业务状态机必须受锁保护；第一个请求改变状态后，第二个请求会看到冲突。

准确表述：

> 单个数据文件采用原子替换思想；`saveAll`跨多个文件仍不是数据库级事务。

## 7. 助教高频问题与回答

### Q1：为什么选择 TCP，不选择 UDP？

TCP 提供可靠、有序的字节流，适合登录、资金和订单状态等不能随意丢失或乱序的业务。代价是 TCP 没有应用消息边界，因此项目自行实现换行分帧。

### Q2：`socket`、`bind`、`listen`、`accept`分别做什么？

- `socket`：创建网络句柄。
- `bind`：把服务端 Socket 绑定到本机 IP 和端口。
- `listen`：把它变成监听 Socket。
- `accept`：接受一个客户端连接，返回新的通信 Socket。

监听 Socket 继续接收新连接，通信 Socket 才负责当前客户端的 `send/recv`。

### Q3：为什么一次 `recv`不能当作一条请求？

因为 TCP 是字节流。一次请求可能被拆成多次 `recv`，多条请求也可能一次收到。项目把字节追加到缓冲区，再按 `\n`逐帧提取。

### Q4：为什么 `send`需要循环？

`send`成功只表示本次写入了返回值对应的字节数，不保证整个字符串一次写完。`sendAll`记录已发送长度，继续发送剩余部分。

### Q5：Token 和 TCP 连接有什么区别？

TCP 连接解决“数据通过哪条通道传输”，Token 解决“请求代表哪个登录身份”。每个需要鉴权的请求都携带 Token，服务端通过 Session 找到角色和用户名。

### Q6：怎么防止客户端伪造管理员身份？

服务端不采用客户端自行声明的角色。登录后角色保存在 Session 中，管理员命令必须通过 `requireAdminSession`，角色不匹配返回 `PERMISSION_DENIED`。

### Q7：为什么客户端也校验，服务端还要再校验？

客户端校验只用于及时提示。客户端可以被修改，网络包也可能被伪造，所以所有安全和业务规则必须在服务端重新检查。

### Q8：怎么防止两个线程同时揽收同一订单？

`pickupExpress`在 `CoreMutex`内完成“检查状态、资金变化、改变状态、保存”。第一个线程完成后，第二个线程读取到的状态不再是待揽收，因此返回 `STATE_CONFLICT`。

### Q9：为什么分成 `CoreMutex`和 `SessionMutex`？

`CoreMutex`保护用户、订单、余额等业务数据；`SessionMutex`只保护 Token 会话表。职责分离，普通会话查询不需要占用业务锁。

### Q10：为什么使用自旋锁？

项目基于当前 MinGW 环境选择 `std::atomic_flag`实现轻量互斥，适用于本课程项目的低并发、短临界区场景。缺点是竞争时会占用 CPU，生产系统更适合标准互斥量或更细粒度锁。

### Q11：密码是如何保存的？

数据文件不保存明文密码，只保存 salt 和 SHA-256 摘要。当前盐值由账号相关信息派生，每个账号通常不同；这是课程项目方案，生产系统应使用随机盐和 Argon2、bcrypt 或 scrypt 等专用密码哈希算法。

### Q12：Token 是怎么生成的？

Token 输入包含账号、角色、高精度时间、两个随机数和对象地址，再计算 SHA-256，得到固定长度摘要。Token 生成使用随机源，和密码盐策略不是一回事。

### Q13：持久化是不是完全事务性的？

不是。单文件保存采用临时文件、备份和重命名，能降低半写入风险；但 `saveAll`依次保存多个文件，不是跨文件原子事务。业务层会恢复内存快照，但已经替换的其他文件无法像数据库事务一样统一回滚。

### Q14：日志为什么能发现篡改？

每条日志的 `currentHash`包含本条内容和上一条 `prevHash`。修改或删除历史记录会导致内容哈希、前后哈希或序号连续性校验失败。

### Q15：Logger 在并发下完全安全吗？

不能过度宣称。大部分业务日志随 `CoreMutex`保护的业务操作串行写入，但 Logger 自身没有独立互斥锁，个别直接审计入口可能并发追加。这是当前版本可继续完善的地方。

### Q16：Session 会自动过期吗？

当前会记录 `lastActiveTime`，但尚未实现空闲超时淘汰。Session 在正常登出或连接断开时清理。生产版本应增加过期时间和定期清理。

### Q17：为什么通知失败不回滚核心业务？

通知是附加功能。订单和资金成功后，即使通知文件暂时保存失败，也不应让真实物流操作失败，因此采用 best-effort，并记录通知写入失败日志。

### Q18：为什么已揽收订单不能改派？

揽收时已经支付快递员提成。此时改派需要设计提成冲正和重新结算，当前版本为保证资金一致性，只允许待揽收订单改派。

### Q19：冻结与停用有什么区别？

冻结是可恢复的账号状态；停用是快递员逻辑移除标记。停用前必须确认没有未完成任务，历史订单仍保留该快递员引用。

### Q20：为什么业务层使用 `ServiceResult`，网络层又有 `Response`？

`ServiceResult`属于业务层，`Response`属于网络协议层。Controller 负责转换，使 LogisticsSystem 不依赖 Socket 和协议格式，便于测试和复用。

### Q21：为什么不使用 HTTP/JSON？

课程项目需要展示传统 Socket C/S。自定义协议能够直接体现 TCP 分帧、转义、长度限制和错误处理。实际生产项目通常优先采用成熟协议和库。

### Q22：客户端能直接访问数据文件吗？

不能。客户端构建只链接菜单、SocketClient、ProtocolCodec和少量校验工具；Repository和LogisticsSystem只编译进服务端。

### Q23：服务端如何支持多个客户端？

主线程持续 `accept`。每接受一条连接就创建工作线程，工作线程维护自己的客户端 Socket 和接收缓冲区，主线程立即继续接受下一连接。

### Q24：项目有哪些已知限制？

- 只监听 `127.0.0.1`，没有远程部署配置。
- 没有 TLS，网络内容未加密。
- Session 没有超时过期。
- 客户端没有自动重连。
- 每连接一个工作线程，不适合超大并发。
- 多文件保存不是数据库事务。
- Logger 没有独立并发锁。
- 密码方案适合课程演示，不等同生产级密码存储。

## 8. 最后一分钟总结话术

> 本项目首先完成了用户、管理员、快递员的完整物流业务闭环，并把单机程序拆成了两个独立进程。客户端只负责交互，服务端统一负责身份、业务和持久化。  
> 在基础要求之上，我实现了自定义 TCP 协议、半包粘包处理、Token 零信任鉴权、多客户端线程模型、并发抢单保护、资金一致性回滚、原子文件替换、哈希链审计、自动调度和通知中心。  
> 同时我也明确当前版本的边界：多文件保存不是数据库事务，Session 暂无超时，Logger 还可以增加独立锁。这些是后续工程化升级方向。
