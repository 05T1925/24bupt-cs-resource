# V3 需求分析

## 1. 题目三边界

V3 是《物流管理平台设计》的第三个独立程序，目标是在 V1/V2 的业务基础上实现网络版。题目强调的是网络架构转型，而不是删减功能。

必须满足：

- 传统 C/S 架构。
- client 和 server 是两个不同进程。
- client 与 server 之间使用 socket 通信。
- 不使用 RPC 框架。
- 功能要求与单机版一致。
- 支持余额不足、非法输入、权限不足、网络异常等错误处理。

## 2. 功能需求

### 2.1 游客能力

- 注册普通用户。
- 登录普通用户。
- 登录快递员。
- 登录管理员。

注册仍由服务端完成输入校验、密码加盐哈希和持久化。客户端只负责收集输入。

### 2.2 普通用户能力

- 修改密码。
- 查询余额。
- 充值。
- 寄件。
- 查询本人发出或接收的快递。
- 查看本人待签收快递。
- 签收本人待签收快递。

服务端必须从 token 解析真实用户身份，不能相信客户端传来的用户名。

### 2.3 快递员能力

- 登录。
- 查看本人待揽收任务。
- 揽收本人任务。
- 批量揽收。
- 查询本人揽收和投递任务。
- 查看个人绩效和收入。

快递员不能揽收未分配给自己的快递，也不能查看其他快递员任务。

### 2.4 管理员能力

- 登录。
- 查看所有用户。
- 冻结/解冻用户。
- 添加快递员。
- 停用快递员。
- 冻结/解冻快递员。
- 查询所有快递。
- 手动分配快递员。
- 自动分配单个快递。
- 一键分配全部待揽收快递。
- 查看统计看板。
- 查看快递员绩效排行。
- 查看操作日志。
- 校验日志哈希链。

停用快递员时仍应保留 V2 的冲突兜底：若名下有未完成任务，服务端拒绝停用并返回阻塞任务清单。

## 3. 继承 V2 的业务规则

### 3.1 多态计费

V3 必须继续保留并实际调用：

```text
ExpressItem::getPrice()
NormalItem   5 元/kg
FragileItem  8 元/kg
BookItem     2 元/本
```

寄件费用由服务端计算，客户端不能提交最终价格。

### 3.2 三状态物流流转

```text
WaitingPickup 待揽收
WaitingSign   待签收
Signed        已签收
```

流转：

```text
用户寄件 -> 待揽收
管理员分配快递员 -> 仍为待揽收
快递员揽收 -> 待签收
收件用户签收 -> 已签收
```

### 3.3 资金流

```text
寄件时：
  用户余额 -= fee
  管理员余额 += fee

揽收时：
  管理员余额 -= fee * 0.5
  快递员收入 += fee * 0.5
```

签收不再发生资金转移。

## 4. 网络版新增需求

### 4.1 协议边界

- 请求和响应必须有明确边界，推荐使用换行分帧。
- 不能假设一次 `recv()` 收到完整请求。
- 所有字段必须经过转义，避免 `|` 和换行破坏协议。
- 服务端需要限制单条消息长度、字段长度和参数数量。

### 4.2 会话安全

- 登录成功后由服务端生成 token。
- 后续请求必须携带 token。
- 服务端通过 token 找到 `role` 和 `username`。
- token 缺失、无效或过期时拒绝请求。
- 日志不能记录明文密码和完整 token。

### 4.3 并发安全

V3 server 可能同时服务多个 client，因此所有业务入口都要考虑并发。第一版建议使用全局互斥锁保护 `LogisticsSystem`：

```text
std::mutex systemMutex
```

后续可以升级为读写锁或按仓储拆锁。

## 5. 错误处理清单

业务错误：

- 用户名重复。
- 用户或快递员不存在。
- 密码错误。
- 账号冻结。
- 余额不足。
- 收件人不存在或被冻结。
- 快递员不存在、冻结或停用。
- 快递状态不允许当前操作。
- 用户签收他人快递。
- 快递员揽收他人任务。
- 重复揽收或重复签收。
- 文件保存失败。

网络和协议错误：

- 客户端连接失败。
- 客户端异常断开。
- 空请求。
- 未知命令。
- 参数数量错误。
- 字段超长。
- token 缺失。
- token 无效。
- 半包和粘包。
- 多客户端并发状态冲突。
