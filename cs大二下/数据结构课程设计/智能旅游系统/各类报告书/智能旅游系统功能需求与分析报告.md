## 1. 引言

### 1.1 编写目的

本报告用于明确智能旅游系统的用户需求、业务需求、功能需求、数据需求、接口需求、AI Agent 需求、非功能需求、算法支撑需求、创新需求、验收标准与能力边界，为总体方案设计、数据结构设计、模块实现、系统测试、课程验收和用户使用说明提供统一依据。

报告不仅描述“系统需要具备什么功能”，还分析各功能满足的实际需求、所依赖的数据与接口、采用的算法和数据结构、性能特点、当前实现程度及风险。所有结论受当前源码、数据库脚本和实测结果约束，不将设计方案、历史文档或 AI 生成内容直接视为已实现事实。

### 1.2 项目背景

旅游用户在校园、景区和城市出行中常面临信息分散、目的地选择困难、路线安排复杂、周边服务不易查找、旅行内容创作成本高等问题。传统页面式查询还要求用户理解系统菜单和参数，难以满足自然语言表达和个性化交互需求。

本系统采用 React + Vite 前端、Spring Boot Java 主业务后端、Python FastAPI Agent 服务的三服务结构，以 MySQL 保存业务数据、Redis 支撑小红书缓存和限流、SQLite 保存 Agent 会话与任务、本地 `uploads` 保存媒体资源。系统把地点查询、建筑设施、推荐排序、路线导航、美食、校园及景区周边、旅行日记、小红书内容增强和 AI 旅游助手整合在同一应用中，并将图、邻接表、Dijkstra、A*、TSP、Haversine、Top-K、Treap、TF-IDF、AC 自动机和 Huffman 编码等课程算法接入具体业务。

## 3. 系统总体需求概述

### 3.1 系统目标

系统目标如下：

1. 提供地点分页、搜索、筛选、详情和推荐，满足快速发现目的地的需求；
2. 提供建筑、设施、附近服务、美食和周边查询，满足到达目的地后的服务查找需求；
3. 提供室内外、单目标和多目标路线规划，辅助安排校园或景区游览顺序；
4. 提供旅行日记管理与 AI 辅助写游记，降低旅行记录和内容创作成本；
5. 提供自然语言 AI 旅游助手，将查询、推荐、路线和生成能力统一为对话入口；
6. 提供小红书热门打卡地等外部内容增强能力，但明确外部平台依赖；
7. 展示数据结构课程中的图、树、堆、字符串匹配、文本压缩、检索、排序和缓存等知识。

### 3.2 系统架构需求

系统采用三服务结构：

- React + Vite 前端运行于 5173 端口，负责页面、交互、空状态、图片 fallback 和 SSE 消费；
- Spring Boot 后端运行于 8080 端口，负责鉴权、业务数据、文件上传、业务算法、统一返回和数据库访问；
- Python FastAPI Agent 运行于 9000 端口，负责意图理解、子 Agent 编排、LLM 调用、工具调用、游记生成和流式事件；
- MySQL 保存用户、地点、建筑、设施、道路、美食、日记、行为、周边和 XHS 扩展数据；
- SQLite 保存 Agent 会话、消息、搭子、任务和偏好；
- Redis 支撑 XHS 热度缓存、发布限流等增强能力；
- 本地 `uploads` 保存图片、视频和 GIF 输出。

### 3.3 用户角色

| 角色 | 主要需求 |
|---|---|
| 游客 | 浏览地点、搜索、查看详情、设施、周边、美食和公开日记。 |
| 注册用户 | 登录后获得用户上下文，管理日记、偏好、行为、Agent 会话和个性化能力。 |
| 旅行规划用户 | 查询附近服务，规划单点、多点或室内外路线。 |
| 内容创作者 | 创建、编辑、评价旅行日记，使用 AI 辅助生成内容和图片素材。 |
| 外部内容使用者 | 查看小红书热门信息、账号状态和发布记录；能力依赖外部平台。 |
| 开发维护人员 | 初始化数据库、执行迁移、维护数据、启动服务、查看 Swagger、日志和测试结果。 |

### 3.4 典型业务场景

用户可在首页浏览热门地点，经搜索和筛选进入地点详情，查看建筑、设施、图片、评分、周边和可选的小红书热度；确定目的地后，可查询附近服务或规划单点、多点路线。旅行结束后，用户可创建日记，或在 AI 助手中输入文字和图片，确认风格后生成标题、正文和标签，再人工编辑并保存。对于不熟悉菜单的用户，Agent 可通过自然语言识别意图、调用 Java 后端工具并以 SSE 逐步返回结果。

### 3.5 当前运行基线

截至 2026 年 6 月 20 日，前端、后端和 Agent 健康检查均返回 HTTP 200；MySQL 初始化与 Flyway 迁移成功；Redis 返回 `PONG`；前端生产构建成功；XHS 运行时识别 43 个方法。后端测试 132 项中 126 项通过、6 项失败；XHS 定向测试 33 项中 29 项通过、4 项失败；前端 lint 仍有 8 个错误和 4 个警告。剩余问题属于代码、测试 Schema 或旧测试契约问题，不是环境缺失。OpenAI Key 采用环境变量复用，没有明文写入项目。

## 4. 用户需求分析

### 4.1 信息发现需求

用户希望在数据量较多时通过分页、类型、关键词、热度和评分快速缩小范围，并在详情页一次看到图片、标签、建筑、设施及增强信息。系统需要在附加信息不可用时保留基础地点内容，避免单一外部依赖阻塞核心浏览。

### 4.2 出行决策需求

用户需要知道目的地附近有什么、距离多远、怎样到达以及多个目标应按什么顺序游览。系统应区分直线距离和路网距离，返回节点、距离和预计时间，并在路网覆盖不足时明确提示不可达或采用有限回退。

### 4.3 个性化与内容需求

用户希望系统结合兴趣、行为、标签和热度给出候选，而不是固定列表；同时希望记录旅行、展示图片并降低写作成本。推荐效果依赖行为和标签数据，AI 文本也必须由用户确认，系统不应将概率性输出当作确定事实。

### 4.4 自然语言交互需求

用户希望直接表达“推荐几个适合拍照的地方”“帮我规划路线”“把这些照片写成游记”等任务。Agent 应完成意图识别、槽位提取、工具路由和结果组织，并在工具或模型失败时返回可理解的提示，而不是伪造结果。

### 4.5 可靠性与可解释需求

用户需要明确的加载、空状态、错误和降级反馈。地点、路线和推荐等核心事实应来自 Java 服务和数据库；小红书热度、AI 生成内容、视觉理解和批量周边数据需要标明来源和质量边界。

## 6. 功能需求分析

### 6.1 用户认证与权限管理需求

认证模块满足用户建立身份、保存个性化数据和区分公开/受保护操作的需求。Java 服务采用 BCrypt 校验密码、JWT 传递身份、Spring Security Filter 写入用户上下文，并以统一 `Result<T>` 返回业务结果。主链路已形成，但当前公开接口范围和异常 HTTP 状态码仍需与测试及安全目标统一，安全权限体系仍需继续完善。

| 编号 | 功能需求 | 实现与验收要点 | 状态 |
|---|---|---|---|
| FR-01 | 用户注册 | 校验用户名和密码，将 BCrypt 密文写入 `sys_user`，重复用户名返回明确错误。 | 已形成核心闭环 |
| FR-02 | 用户登录 | 校验凭据，成功后签发 JWT，失败返回 401 类错误。 | 已形成核心闭环 |
| FR-03 | JWT 鉴权与用户上下文 | Filter 解析 Token，将用户信息写入 SecurityContext，Java Agent 代理从 Principal 取 userId。 | 已形成核心闭环 |
| FR-04 | 公开与受保护接口区分 | 浏览类接口可公开，用户数据修改应受保护；现有日记 POST、XHS 范围仍需收紧复核。 | 存在遗留问题 |
| FR-05 | 认证异常与统一返回 | 以 `code/message/data` 返回异常；旧测试仍期待部分业务错误 HTTP 200，需要统一合同。 | 基本可用 |

### 6.2 地点浏览、搜索与详情需求

地点模块满足用户快速查找目的地、比较热度与评分、查看完整信息的需求。`spot_place` 约 301 条数据，配合 `Page<T>`、MyBatis-Plus 条件构造器、LIKE、排序和 JSON 标签解析。详情可聚合建筑、设施和 XHS 信息；增强查询失败时应保留基础地点结果。

| 编号 | 功能需求 | 实现与验收要点 | 状态 |
|---|---|---|---|
| FR-06 | 地点分页浏览 | 输入 page、size，返回 records、total 等分页信息，减少一次性传输。 | 已形成核心闭环 |
| FR-07 | 地点类型筛选 | 按校园、景区或其他类型组合查询。 | 已形成核心闭环 |
| FR-08 | 关键词搜索 | 对名称、关键词或描述进行 LIKE/检索匹配；无数据时返回空列表。 | 已形成核心闭环 |
| FR-09 | 地点详情查看 | 根据 placeId 返回基础信息、坐标、开放时间、评分和描述。 | 已形成核心闭环 |
| FR-10 | 热门 / 高评分展示 | 按 clickCount、rating 等字段排序并限制数量。 | 已形成核心闭环 |
| FR-11 | 聚合建筑、设施、XHS 信息 | 关联 `spot_building`、`spot_facility` 和可选 `spot_xhs_info`；XHS 异常不阻塞基础详情。 | 基本可用 |

### 6.3 推荐与排序需求

### 6.6 路线规划与导航需求

### 7.1 数据关系要求

地点是多数业务的中心实体：建筑、设施、美食、道路边、日记、周边和 XHS 热度通过 `place_id` 与地点关联；用户通过作者、行为、账号和 Agent 会话参与业务。维护时必须保证外键语义和业务 ID 一致，即使部分表未使用数据库物理外键，也不能产生无主记录。

### 7.2 数据质量要求

坐标需要满足经纬度范围并避免大量不合理重复；道路距离和速度必须非负；JSON 字段应保持合法；图片路径应可访问；导入脚本需统一 UTF-8；小红书数据需保存刷新时间和过期状态；测试表结构必须随生产迁移同步。对生成或批量补充数据应保留来源标签，不能与已核实真实 POI 混为一谈。

## 8. 接口需求分析

### 8.1 REST API 需求

所有 Java 业务接口应采用统一 `Result<T>`，至少包含 `code`、`message`、`data`。分页结果应明确 records/items、total、page、size 等字段，避免 Java 与 Python Agent 对同一返回结构理解不一致。

| 接口类别 | 典型方法与路径 | 输入 | 输出 | 鉴权与失败情况 |
|---|---|---|---|---|
| 认证 | POST `/api/auth/register`、`/login`；GET `/me` | 用户名、密码、JWT | Token 或用户信息 | 注册登录公开；`me` 需登录；重复用户名、密码错误 |
| 地点 | GET `/api/places`、`/search`、`/{id}`、`/hot`、`/recommend` | page、size、query、type、limit、id | 分页地点、详情、推荐 | 浏览可公开；无数据、参数错误、增强查询失败 |
| 建筑 | GET `/api/buildings/**` | placeId、buildingId、type | 建筑列表/详情 | 无场所或无建筑返回空/404 语义 |
| 设施 | GET `/api/facilities/**`、`/nearby`、`/nearest` | placeId、buildingId、type、坐标、半径 | 设施和距离 | 坐标非法、无候选、路网不可达 |
| 导航 | GET/POST `/api/navigation/**` | start、end、destinations、algorithm、mode | 节点、分段、距离、时间 | 节点不存在、路网断开、Provider 不可用 |
| 美食 | GET `/api/foods/**` | page、size、placeId、cuisine、limit | 列表、详情、热门 | 数据不足返回空；Agent 字段合同需统一 |
| 日记 | GET/POST/PUT/DELETE `/api/diaries/**` | 标题、正文、地点、媒体、评分等 | 日记或操作结果 | 写操作应校验身份；正文为空、权限不足、Schema 不一致 |
| 周边 | GET `/api/surroundings/**` | placeId、type、query、坐标、radius | 分页列表、详情、分类统计 | 乱码、空结果、坐标错误 |
| XHS | `/api/xhs/**`、地点 refresh、日记发布 | placeId、userId/Principal、Cookie 状态、diaryId | 热度、账号状态、发布记录 | Cookie 失效、平台失败、限流、缓存为空；权限需加强 |
| 上传 | POST `/api/upload/**` | multipart 文件 | 资源路径、元数据 | 类型/大小不合法、写盘失败 |
| Agent 代理 | `/api/agent/**` | message、sessionId、图片、生成参数 | 同步结果或流 | Java 负责认证；Python 不可达、超时、工具失败 |
| 算法演示 | `/api/algorithm/**` 等 | 数组、文本、图参数 | 排序、搜索、压缩等结果 | 主要用于课程展示，不等同全部业务主流程 |

接口命名、查询参数和返回字段必须形成单一契约。当前 `tourism_api.py` 与 Java 在地点搜索参数、热门数量、美食分页、路线起终点、多点路线和最近设施等处存在历史错位，后续应以 OpenAPI 或契约测试锁定。

### 8.2 SSE 流式接口需求

AI 助手需要以 SSE 增量输出，避免用户等待完整生成结果。事件至少包括：

| 事件 | 作用 | 前端处理 |
|---|---|---|
| `token` | 增量文本片段 | 按顺序拼接到当前消息 |
| `tool_call` | 告知即将调用的工具和有限参数摘要 | 展示“正在查询/规划”状态，避免暴露敏感值 |
| `tool_result` | 工具调用结果或摘要 | 更新卡片、路线或结构化内容 |
| `done` | 生成结束，附 metadata | 固化消息；解析日记卡片、图片和任务信息 |
| `error` | 模型、工具、网络或参数错误 | 停止加载并展示可恢复提示 |

流式接口应保证事件顺序、UTF-8 编码、断连处理和会话关联。日记生成需在 `done` 元数据中保留标题、正文、标签和图片路径；前端对历史图片进行聚合时应去重。异常时可以返回已有部分文本，但必须标记未完成。

### 8.3 Java 与 Python Agent 接口需求

Java 负责 JWT 鉴权、用户上下文、业务数据、上传、日记保存和确定性算法；Python 负责 LLM、意图理解、Agent 编排、工具选择、游记生成和流式响应。Python 工具通过 `tourism_api` 调 Java，不能绕过 Java 数据层自行编造地点、路线和美食事实。

跨服务合同应统一：

1. 参数名称、必填项、枚举值和默认值；
2. `Result<T>` 与分页字段；
3. 认证头和用户身份来源；
4. 超时、重试、空结果和错误码；
5. 搜索、美食、路线、最近设施等重点工具的契约测试；
6. Java 未代理的会话重命名、标题建议、标签提取和图片描述端点的调用路径。

## 10. 算法与数据结构需求分析

| 算法 / 数据结构 | 所属功能 | 输入 → 输出 | 核心思想与选择依据 | 复杂度 / 性能 | 接入程度与边界 |
|---|---|---|---|---|---|
| 图 / 邻接表 | 路线导航 | 路网边、节点 → 内存图 | 稀疏路网使用邻接表节省空间，便于遍历邻边 | 空间 `O(V+E)` | 路线核心结构；依赖节点和边覆盖 |
| Dijkstra | 最短路、最近设施、室内路径 | 起点、权重图 → 最短距离和路径 | 非负权下逐步确定最短距离，优先队列优化 | `O((V+E)logV)` | 核心业务算法；断图时不可达 |
| A* | 单目标导航 | 起点、终点、模式 → 路径 | `f=g+h`，Haversine 作启发，目标明确时减少扩展 | 最坏接近 Dijkstra | 核心算法；启发值和坐标质量影响效率 |
| TSP / 多目标 | 多点游览 | 起点、目标集 → 顺序和分段 | 小规模 DP 求较优/最优顺序，较大规模启发式近似 | DP `O(n²2ⁿ)` | 增强算法；启发式不保证全局最优 |
| Haversine | 附近、周边、A* | 两点经纬度 → 球面距离 | 无需路网即可估算地理直线距离 | 单次 `O(1)`，扫描 `O(n)` | 已接入；不能代替实际道路距离 |
| Top-K / Treap | 推荐、热门 | 候选分数流 → 前 K | Treap 维持键序和随机堆平衡，减少全量排序 | 平均 `O(n log k)` | 课程核心结构；小数据可直接排序 |
| TF-IDF | 文本检索 | 查询、文档集 → 相似度排序 | 词频与逆文档频率突出区分性词项 | 约 `O(ND)` | 用于算法/日记检索场景，不代表所有搜索均使用 |
| Jaccard / 模糊匹配 | 标签和关键词 | 两集合或文本 → 相似度 | 交并比或包含关系，适合短标签 | 集合约 `O(a+b)` | 推荐和检索辅助 |
| 余弦相似度 | 内容推荐 | HashMap 特征向量 → 相似度 | 比较向量方向，适合稀疏兴趣特征 | 单候选 `O(D)` | 课程设计级，依赖特征质量 |
| 协同过滤 | 行为推荐 | 用户行为矩阵 → 候选 | 利用相似用户行为加权 | 约 `O(UD+UI)` | 实现存在，主流程效果受行为稀疏与接入限制 |
| AC 自动机 | 日记过滤 | 敏感词集、正文 → 命中/过滤文本 | Trie + fail 指针一次扫描多模式 | `O(L+z)` | 已接入日记，词库质量决定效果 |
| Huffman 编码 | 日记压缩 | 字符频率、正文 → 编码/原文 | 高频字符使用较短前缀码 | 构树 `O(σlogσ)`，编解码 `O(L)` | 课程算法封装，不是通用存储平台 |
| JSON 字段 | 用户、地点、日记、道路 | 列表/对象 ↔ JSON | 支持兴趣、标签、图片、交通方式等可扩展结构 | 解析与长度线性相关 | 灵活但需 Schema 约束和异常处理 |
| `Page<T>` | 各列表 | 页码、大小、条件 → records/total | 数据库分页避免全量传输 | 依 SQL 和索引 | 地点、日记、周边等广泛使用 |
| MyBatis-Plus Wrapper | 动态查询 | 条件 → SQL | 组合筛选、排序和分页 | 由数据库计划决定 | 工程查询结构，不包装为自研算法 |
| JWT Token | 认证 | 凭据 → Token → Principal | 签名令牌支持无状态认证 | 单请求与 Token 长度近线性 | Java 主链路使用；密钥和权限仍需加固 |
| ToolRegistry | Agent | 工具名、Schema、参数 → 结果 | 哈希映射注册查找，按 Agent 隔离 | 平均查找 `O(1)` | Agent 核心结构；工具合同需测试 |
| SSE 事件流 | AI 助手 | 生成事件 → 浏览器增量消息 | 异步生成器持续推送，降低首字等待 | 传输与事件数线性 | 已实现 token/tool/done/error |
| Redis 缓存 | XHS | 外部结果 → 缓存 → 展示 | 通过 TTL 减少重复外部访问 | 命中通常近 `O(1)` | 增强能力；需处理缓存击穿与不可用 |
| Fibonacci Heap | 算法扩展 | 键值 → 堆操作 | 合并、插入和减键具有较好摊还界 | 插入摊还 `O(1)` 等 | 有实现和测试；未作为主路线优先队列 |

### 10.1 算法选择综合分析

路线问题选择邻接表是因为当前道路图相对稀疏；单目标路线用 A* 可以利用坐标启发，而需要稳定最短距离或多源扩展时使用 Dijkstra。多点路线在目标数量少时可用动态规划，目标增加后指数复杂度不可接受，因此切换启发式算法。附近查询采用 Haversine 能在无完整路网时快速估算，但不代表实际步行距离。

推荐模块以 HashMap 稀疏向量、余弦相似度和 Top-K 为主，适合课程规模；当行为数据不足时，协同过滤难以发挥，应回退内容和热度推荐。AC 自动机和 Huffman 将字符串数据结构与日记业务结合，前者解决多敏感词匹配，后者展示前缀编码思想。

## 14. 需求约束与能力边界

| 约束类别 | 事实边界 | 影响与要求 |
|---|---|---|
| 数据覆盖 | 只有数据库已有地点、坐标和服务可查询 | 无数据时返回空或提示，不生成虚假地点 |
| 路线规划 | 依赖 `spot_road_edge`、坐标、入口和连通性 | 不保证任意城市或任意两点可达 |
| XHS 平台 | 依赖 Cookie、外部接口、反爬、账号、Redis/MySQL 缓存 | 不承诺稳定抓取或发布；必须降级 |
| AI 模型 | 文本和视觉模型能力不同，输出具有概率性 | DeepSeek 等文本模型不理解图片；内容需人工确认 |
| 图片资源 | 本地相对路径可能无法被云模型访问，且有缺图和重复风险 | 需上传、路径转换、fallback 和去重治理 |
| 基础设施 | MySQL 是业务主库，SQLite 是 Agent 本地库，Redis 主要支撑 XHS | 服务不可用时按模块提示，不能静默伪造成功 |
| 测试与生产差异 | H2 表结构落后于 MySQL/Flyway | 需同步 Schema，避免假失败和异常被吞后的假通过 |
| 前端降级 | `safe()`、空状态和图片隐藏改善体验 | 降级内容不得冒充真实数据，同时应增强可观测性 |
| 权限与安全 | Java 部分接口公开范围偏宽，Python 直连可接受请求 user_id | 需收紧授权、服务间鉴权和密钥配置 |
| 课程规模 | 当前数据和单机架构适合课程演示 | 大规模需空间索引、分布式缓存、异步队列等 |
| 质量遗留 | 后端 126/132；XHS 29/33；lint 8 错误、4 警告 | 不能写“全部通过”；剩余为代码/旧测试契约问题，非环境缺失 |
| 密钥管理 | OpenAI Key 通过环境变量复用，没有明文写入项目 | 报告和日志不得输出 Key |

## 18. 总结

本项目围绕智能旅游场景形成了较完整的功能需求体系，覆盖地点、路线、建筑设施、附近服务、周边、美食、旅行日记、AI 助手、小红书增强、媒体和数据维护等模块。核心地点、日记和基础业务形成了可运行闭环，多项增强能力在课程设计范围内基本可用。

从数据结构课程角度，系统把图和邻接表、Dijkstra、A*、TSP、Haversine、Top-K/Treap、TF-IDF、余弦相似度、AC 自动机、Huffman 编码、分页和哈希工具注册等结构与算法映射到真实业务，并分析了输入输出、复杂度、选择依据和能力边界。

大模型与智能体在需求梳理、系统设计、算法比较、缺陷分析、测试计划和文档整理中发挥了辅助作用；系统中的 Agent 也承担意图识别、路线辅助、工具调用和游记生成。但 AI 输出必须由人工确认，业务事实仍以 Java 服务和数据库为准。

系统目前仍存在测试契约、H2 表结构、前端 lint、跨服务参数、数据质量、安全配置、外部平台和视觉模型等边界。当前可准确表述为：主要运行环境已启动，核心服务健康检查通过，前端生产构建成功；后端测试 126/132 通过，XHS 测试 29/33 通过，仍有代码和旧测试契约遗留问题。

本报告可作为总体方案、数据结构和数据字典、模块设计、测试报告、评价改进报告和用户使用说明的需求基础。后续报告除继续采用相同事实口径和分层状态描述外，还应统一采用以下贡献口径：王博生主责前后端与仓库管理，刘文涛主责数据库、算法与报告撰写，胡文龙主责 Agent 全流程与前端美化，三人共同参与联调和验收。
